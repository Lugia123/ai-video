# 当你的用户是 AI：给 agent 做产品设计的八条原则

> 系列视频分镜脚本（中文口播）

## 系列信息

- **系列名**：当你的用户是 AI —— 给 agent 做产品设计
- **总论点**：AI agent 也是一种用户，只是弱点和人不一样——它不读手册、会忘事、会绕路、会把 ok 当真。传统 UX 原则大多仍成立，但要换个方向用。
- **贯穿全系列的一句话**：「报告说的」和「实际发生的」之间要有连线。
- **目标观众**：用 AI agent 做开发、或者在做 agent 产品的开发者与产品经理。不需要用过 Polter。
- **每集时长**：60–90 秒。
- **案例来源**：Polter，一个 Ghostty 终端的分叉，让一个 AI agent（「总管」）通过 MCP 工具监管其他终端里的 agent（「worker」）：群聊、任务面板、静止感知、按住/护盾标记。**它只作为证据出现，不是主角。** 每集先讲通用问题，再用它的设计文档里的真实记录佐证。
- **事实纪律**：所有数字与引语都能在仓库 `dev-docs/poltergeist/` 里找到出处，逐集列在「事实核对」表。核对不到的已删去或标注（未核实）。

### 片头语（每集开头 3 秒，统一）

> 「你的新用户不读手册、会忘事、会绕路，还会把 ok 当真。它是 AI。」

画面：终端网格里几个光标在同时闪；字幕打出系列名。

## 第1集：程序报事实，模型做判断

**一句话原则**：程序只负责量它确定知道的东西；「这意味着什么」交给模型。

**行业概念：机制与策略分离（Separation of Mechanism and Policy）**
通用解释：底层只提供「能做什么、测到了什么」的机制，「据此该怎么办」的策略放在上层、可替换。放到 agent 产品里：程序出传感器读数，模型出判断——别把判断写死在代码里。

**时长估计**：约 90 秒（旁白约 360 字）

### 可迁移清单

1. 列出你给 agent 的每个状态字段，逐个标注「测量值」还是「推断值」；推断值要么删，要么改成它依赖的原始读数。
2. 给「分子和分母」而不是只给「比例」，给「两个时长」而不是一个「状态」——让模型自己合成判断。
3. 找出那些「程序本来就确定知道、却没报」的事实（退出码、耗时、进程是否还在），补上。
4. 凡是「只在状态变化时才上报」的读数，确认下游不会拿「没收到消息」当「没变化」；需要的话加心跳。
5. 任何依赖对方 UI 文案做模式匹配的逻辑，都视为会在对方下一次升级时失效。

## 第2集：注意力是预算，打断有成本

**一句话原则**：对 agent 来说，每一条「顺便看一下」都花掉它的上下文；打断要按预算花。

**行业概念：注意力经济 / 打断成本（Cost of Interruption）**
通用解释：信息的丰富会造成注意力的贫乏（Herbert Simon）。人被打断要花时间回到原任务；agent 被打断要花 token、挤掉上下文。对 agent，「能看见」和「该被叫醒」应当是两件事。

**时长估计**：约 90 秒（旁白约 360 字）

### 分镜脚本

| 时间码 | 画面 | 旁白（口播，可直接配音） | 屏幕字幕 |
| --- | --- | --- | --- |
| 0:00–0:08 | 群聊里总管一条接一条发长消息，三个 worker 头上的通知数字不停跳 | 「多说一句总没坏处」——对人也许是。对 agent，你说的每一句，都要从别人的上下文里扣钱。 | 每一句都要扣钱 |
| 0:08–0:22 | 动画：一个「上下文」进度条，每来一条通知就被吃掉一截 | agent 最稀缺的不是 CPU，是上下文。一条群消息发给三个人，就是三次打断、三份全文进三个上下文。而发消息的那一方，通常完全看不到这个账单。 | 稀缺的是上下文，不是 CPU |
| 0:22–0:45 | 录屏重建（示意）：一个 worker 屏幕上反复出现 `[poltergeist] N new messages`；角落计时 11 分钟、44.5k tokens、写文件数 0 | Polter 做过一次实测：总管监管三个 agent，二十分钟里往群里发了 6 条消息，每条都唤醒全部 3 个 worker。其中一个 worker 花了 11 分钟、44.5k tokens，相当一部分在读总管的话，一个文件都还没写。 | 11 分钟 · 44.5k tokens · 0 个文件 |

| 0:52–1:10 | 表格动画：「未读」一列、「唤醒」一列；被监管的 worker 那行「唤醒=否」、「未读=照常」 | 修法分两步。第一，被监管的终端不因群消息被叫醒。但未读计数一个字不改——「不打断」不等于「看不见」。能看见和该被叫醒，是故意分开的两个数。 | 不打断 ≠ 看不见 |
| 1:10–1:20 | 代码卡片：`group_post(group, text, mention: ["0x2528…"])`；正文里的 `@xxx` 被打叉 | 第二，真要叫某个人，点名是参数：一个终端 id 的数组，而不是去解析正文里的 @。解析错的方向是点错人，那等于往没被点名的终端里敲回车。 | 点名是参数，不是文本 |
| 1:20–1:30 | 检查清单浮现 | 回去数一数：你的系统里，一条消息会叫醒几个 agent？ | 一条消息叫醒几个？ |

### 可迁移清单

1. 为每一种会推送给 agent 的消息，算出它的扇出：一条 × 收件人数 × 平均读入长度。
2. 把「可以读到」（未读/收件箱）和「会被打断」（唤醒/注入）拆成两个独立字段，默认只打断真正需要的角色。
3. 定向投递用结构化参数（id 列表），不要从自然语言里解析 @。
4. 让发送方看得见代价：扇出次数、被打断次数、读入字节数——这些是你自己系统里就有的数。
5. 能进「状态面板」的信息，就别用「广播消息」传。

### 素材清单

- 录屏重建：worker 屏幕反复出现新消息提示（用测试实例重演，**不要**用原始会话录屏；需打码：会话标题、目录路径、群名）。
- 动画：上下文进度条被吃掉；「未读 / 唤醒」两列表格。
- 代码卡片：`group_post` 的 `mention` 参数（id 用文档中的截断形式 `0x2528…`）。

## 第3集：引导放在决策那一刻

**一句话原则**：引导要在 agent 选工具之前到达，而且只在「此刻真的相关」时出现。

**行业概念：即时引导（Just-in-Time Guidance）；告警疲劳（Alert Fatigue）**
通用解释：即时引导是把帮助放在用户正要做决定的那个位置和时刻，而不是放进一本需要主动去翻的手册。告警疲劳是反面：一个每次都出现的提示会被习惯性忽略，最后比没有更糟。

**时长估计**：约 90 秒（旁白约 360 字）

| --- | --- | --- | --- |

| 0:08–0:20 | 动画：「看到工具列表 → 选工具 → 读文档」三步，前两步已经走完，第三步从未发生 | 很多 agent 的文档是两段式的：常驻的只有名字和一句描述，正文要主动去读。所以决定往往发生在读之前。 | 常驻的只有一句描述 |

### 可迁移清单

1. 画出 agent 做关键选择的时刻（选工具、选路径），确认你的关键引导在那之前就已进入上下文，而不是等它主动检索。
2. 把「有什么工具」的清单升级为「什么处境用什么」的索引。
3. 所有运行时提示都写明触发条件；能用两三个可判定条件卡窄的，就不要每次都出现。
4. 提示内容用当前事实（「面板是空的」），不用劝告（「建议你使用面板」）。
5. 对每一条提示做负对照：拆掉某个触发条件，确认它会在不该出现时出现——证明条件真在起作用。

- 时间线动画：总管与 4 个 worker 的一晚（重建示意，不用原始会话；需打码：任何会话标题、目录、机器名）。
- 引文卡：总管自述原话（只取文档中那一句）。

## 第4集：约束由系统执行，不写在提示里

**一句话原则**：不许 agent 做的事，要让它在代码里做不出来；而且定约束的一方不能是被约束的一方。

**行业概念：防呆（Poka-yoke）；职责分离（Separation of Duties）**
通用解释：防呆来自丰田生产体系——与其提醒工人别装错，不如把零件做成装错了就装不进去。职责分离是安全领域的老规矩：批准的人和执行的人不能是同一个。对 agent 而言，写在提示词里的禁令会随长上下文被挤走；写在工具入口的拒绝不会。

## 第5集：先设计失败长什么样

**一句话原则**：失败要出声；「我不知道」和「我知道，答案是没有」必须是两个不同的回复。

## 第6集：能力对等，不开后门

**一句话原则**：人在界面上能做的事，agent 应当走同一条代码路径也能做；少数例外要讲清楚为什么。

**行业概念：能力对等（Capability Parity）；单一代码路径（No Side Door）**
通用解释：如果产品只给 agent 开放人类能力的一小部分，agent 不会就此放弃，它会找别的路——脚本、模拟点击、系统自动化——而这些路既不受你的权限约束，也不留记录。让 agent 和人走同一个入口，权限和日志才管得住它。

## 第7集：程序不替人做身份判断

**一句话原则**：能恢复的事实自动恢复；「这是不是同一个」这种身份判断，交给读得懂上下文的一方。

**行业概念：实体解析的静默误配（Silent Mis-match in Entity Resolution）；人（或 agent）在回路（Human-in-the-Loop）**
通用解释：把两份记录判定为「同一个东西」叫实体解析。它最贵的错误不是「认不出」，而是「认错了，而且看起来一切正常」。当程序手上的线索不足以区分时，就不该由程序做这个判断。

**时长估计**：约 85 秒（旁白约 340 字）

### 可迁移清单

1. 把「恢复 / 同步 / 合并」逻辑里每个「判定为同一个」的地方标出来，问：线索足以唯一确定吗？
2. 线索不足时，程序恢复的是「材料」（目录、标题、记录），把配对交给有上下文的一方。
3. 区分「事实」（编号、状态、名字）和「身份」（这个活体对象是不是那个），前者自动，后者显式确认。
4. 检查所有自动恢复的对象之间的依赖：恢复了 A 而没恢复 A 所依附的 B，会造出一个谁都没想要的状态。
5. 对误配做一次演练：故意让两个对象线索相同，看系统是报「无法区分」还是静默挑一个。

## 第8集：写下不做什么

**一句话原则**：一份写明「不做什么」的清单，比功能清单更能保护产品；而数字一旦被当成目标，就不再说真话。

**行业概念：反目标（Non-goals / Anti-goals）；古德哈特定律（Goodhart's Law）**
通用解释：反目标是明确写下「这个产品不解决什么」，让每个新需求先过这道线。古德哈特定律说：一个指标一旦成为目标，它就不再是好指标。给 agent 的面板和统计尤其如此——它会照着你画的东西去优化。

**时长估计**：约 90 秒（旁白约 360 字）

### 可迁移清单

1. 给你的 agent 产品（或其中一个面板）写一段「不存什么 / 不做什么」，并规定新增字段必须先改这段。
2. 每个展示给 agent 或人的指标，先用一份真实数据跑一遍，看它会不会讲出一个错误的故事。
3. 面板只摆可计算的事实（多久没动、指派了几次），把「卡住了 / 效率低」这类判断留给读过内容的一方。
4. 所有周期性汇报改为事件触发，并默认「没事就不写」。
5. 允许修正已记录的内容，但要保持标识不变、修改留痕。
